04: What Changed and Why

One interaction change gave users the confidence to trust the filter

Most of the filter system shipped close to where it started. But one thing testing made clear: users had no way of knowing if their filter selections had actually been applied to the results.

V1: Initial design
Sort & Filter button with no change state

The button looked the same whether zero or five filters were active. Users tapped it, made selections, and then second guessed themselves. They could not tell if their changes had been applied to the results at all.

→
V2: After testing
Active state showing filter count

When filters are applied, the button shifts to a dark blue state and displays the number of active filters. Users immediately understood their selections were live. Task success on the filter scenario went from 5/10 to 10/10.

06: What I Learned

What I learned and what I would carry into any team

Constraints are design inputs, not blockers
The API limitation forced a better, more accessible interaction. Apply on release is now a reusable pattern across the product. Screen reader users benefit more from it than from a live drag update.
Data wins stakeholder buy in
"7 of 10 users failed" changed how leadership engaged with the design process more than any visual or prototype. Framing research findings in failure rate language made the problem feel urgent and fixable.
Ask what the design needs to support in 18 months, not just this sprint
The Sort and Filter architecture I built is intentionally extensible. Adding EV filters or accessibility options requires no structural redesign, because I asked what else this would need to do before locking the component structure.
Writing clearly for engineers is as important as designing for users
I mentored a junior designer on component annotation during this project. Well documented Figma files cut dev questions by an estimated 30%. A well annotated handoff is design leadership, not admin work.
